# Feature Specification: Friday 记忆系统重构

**Feature Branch**: `011-memory-refactor`

**Created**: 2026-06-06

**Status**: Draft

**Input**: 重构 Friday 的记忆系统。Friday 的记忆系统是 Friday 自身的功能——用于在 Friday 与用户的对话中自动记住用户信息、偏好和习惯，让 Friday 越用越了解用户。这与 Friday 项目的开发过程完全无关（开发过程由 Claude Code + claude-mem 管理）。当前记忆系统混入了面向开发过程的文件记忆功能，定位不清，需要清理。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 对话中自动记住用户信息 (Priority: P1)

用户在与 Friday 闲聊时提到"我是做后端开发的，主要用 Python"，Friday 自动将这条信息存入记忆。下次用户问"帮我写个脚本"时，Friday 已经知道用户偏好 Python，直接用 Python 回答而不需要再问。

**Why this priority**: 这是记忆系统最核心的价值——让 Friday 不用每次都从零开始了解用户。没有自动记忆，Friday 就是个无状态的聊天机器人。

**Independent Test**: 可以通过连续两次对话验证——第一次提到偏好，第二次询问相关问题，检查 Friday 是否基于记忆给出了个性化回答。

**Acceptance Scenarios**:

1. **Given** 用户首次与 Friday 对话，**When** 用户在对话中提到"我喜欢用 vim 编辑器"，**Then** 这条偏好信息被自动存入记忆系统
2. **Given** 用户之前提到过"我做后端开发"，**When** 用户在新的对话中问"帮我推荐一个编辑器"，**Then** Friday 的回答中体现了对用户偏好的了解（不需要重新询问）

---

### User Story 2 - 记忆上下文自动注入 (Priority: P1)

用户每次发消息时，Friday 自动从记忆库中检索与当前对话相关的记忆，注入到对话上下文中。检索关键词基于用户当前消息内容，而非固定的硬编码关键词。

**Why this priority**: 如果记忆存在但不被使用，等于没有。自动注入是让记忆真正发挥作用的机制。当前实现使用硬编码关键词"用户偏好 习惯 设置"，导致大量记忆无法被召回。

**Independent Test**: 用户在记忆库中有"我对花生过敏"的记录，当用户问"今天中午吃什么好"时，Friday 的回答中主动避开了含花生的食物建议。

**Acceptance Scenarios**:

1. **Given** 记忆库中有"用户住在上海"，**When** 用户问"明天天气怎么样"（未提到地点），**Then** Friday 自动关联到上海并给出上海天气
2. **Given** 记忆库中有"用户习惯用 Python"，**When** 用户问"帮我排序一个列表"，**Then** Friday 直接给出 Python 示例而非问"你想用什么语言"
3. **Given** 用户当前话题与已有记忆完全无关，**When** 检索结果为空或分数很低，**Then** 不注入无关记忆，避免干扰对话

---

### User Story 3 - 清理不属于用户产品的记忆功能 (Priority: P2)

移除当前记忆系统中面向开发过程的功能（文件记忆：决策记录、经验教训、项目宪法），这些内容属于 Claude Code + claude-mem 管理的开发流程，不属于 Friday 与用户的对话交互。

**Why this priority**: 功能定位不清会导致后续维护混乱和用户困惑。清理后记忆系统的职责边界更清晰——只服务于用户对话。

**Independent Test**: Friday 运行时不再加载或引用任何文件记忆相关的内容，记忆模块的公开接口中不再暴露决策记录、经验教训等与用户对话无关的功能。

**Acceptance Scenarios**:

1. **Given** Friday 重构后的记忆系统，**When** 用户通过对话查询记忆，**Then** 只返回动态记忆内容，不包含开发过程的决策/教训/宪法
2. **Given** Friday 重构后的代码，**When** 检查记忆模块的对外接口，**Then** 不存在文件记忆相关的公开函数或工具

---

### User Story 4 - 记忆数据存储到用户数据目录 (Priority: P2)

记忆数据应存储在用户专属数据目录下，而非项目源码目录中。确保记忆数据跟随用户，不跟随项目代码。

**Why this priority**: 数据归用户所有，不应混入开发仓库。当前动态记忆存在项目根目录的 `.friday-memory/`，如果用户重新 clone 项目，记忆就丢了。

**Independent Test**: 检查记忆数据的实际存储路径，确认在用户数据目录下而非项目目录下。

**Acceptance Scenarios**:

1. **Given** Friday 的记忆数据存储配置，**When** Friday 初始化记忆系统，**Then** 数据存储在用户数据目录下
2. **Given** 用户数据目录下无记忆数据，**When** Friday 首次启动，**Then** 自动在用户数据目录下创建记忆存储，无需迁移旧数据

---

### Edge Cases

- 记忆系统初始化失败时（如磁盘空间不足），Friday 应仍能正常对话，只是没有记忆功能
- 记忆库为空时（首次使用），不应报错，只是检索返回空结果
- ~~用户说"忘掉我说过 xxx"时，系统应能删除对应记忆~~（暂不开放，记忆由系统自动管理）
- 记忆自动注入不应导致 system prompt 过长，需要限制注入的记忆条数

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 记忆系统 MUST 只保留动态自动记忆功能，移除所有文件记忆相关功能（决策记录、经验教训、项目宪法）
- **FR-002**: 记忆系统 MUST 在用户对话过程中自动从对话内容中提取值得记住的信息并存入记忆库
- **FR-003**: 记忆系统 MUST 在每次用户发消息时，基于用户当前消息内容从记忆库中检索相关记忆
- **FR-004**: 检索到的相关记忆 MUST 自动注入到对话上下文中，作为 LLM 的参考信息
- **FR-005**: 记忆检索 MUST 使用用户当前消息内容作为查询关键词，而非硬编码的固定关键词
- **FR-006**: 记忆注入 MUST 有数量上限，避免上下文过长
- **FR-007**: 记忆系统初始化失败时 MUST 降级运行，不影响基本对话功能
- **FR-008**: 记忆数据 MUST 存储在用户数据目录下，不存储在项目源码目录中
- **FR-009**: 记忆模块的对外接口 MUST 只暴露与用户对话相关的动态记忆操作

### Key Entities

- **动态记忆条目**: 一条自动提取的用户信息，包含内容文本、相关度分数、创建时间。由对话中自动产生，用于未来对话的上下文注入

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户在对话中提到的偏好信息，在后续对话中能被自动引用，无需用户重复说明
- **SC-002**: 记忆检索基于用户当前消息内容，与对话主题相关的记忆召回率显著高于硬编码关键词方案
- **SC-003**: 记忆模块的公开接口中不包含任何文件记忆相关功能，代码和接口层面完全干净
- **SC-004**: 记忆数据存储在用户数据目录下，项目源码目录中不包含任何运行时记忆数据
- **SC-005**: 记忆系统不可用时，Friday 的基本对话功能不受影响

## Assumptions

- **Friday 的记忆系统是 Friday 自身的功能**，用于在 Friday 与用户的对话交互中自动记住和回忆用户信息。这与 Friday 项目的开发过程完全无关——开发过程由 Claude Code + claude-mem 独立管理，不在本次重构范围内
- 动态记忆的核心能力（自动提取、语义检索）由 Mem0 库提供，本次不替换底层实现
- 用户数据目录的路径约定与 Friday 现有配置一致（`~/.friday/`）
- 旧路径 `.friday-memory/` 中的数据不需要迁移，直接废弃即可
- `memory/adapter.py` 作为记忆模块的统一入口，重构后只代理动态记忆功能
