# 功能规格：指令系统存储统一到知识库

**功能分支**: `014-unify-instruction-storage`

**创建日期**: 2026-06-08

**状态**: 草稿

**输入**: 用户描述: "将指令系统的存储和检索合并到知识库，统一存储层，保留独立的指令执行层"

## 用户场景与测试

### 用户故事 1 - 通过对话教会 Friday 新指令 (优先级: P1)

用户对 Friday 说"以后每次我说部署，你就执行 git push origin main"。Friday 理解意图后，将这条指令作为一条特殊类型的知识条目存入知识库。之后用户说"帮我部署"时，Friday 能通过语义检索（而非字面匹配）找到这条指令，识别出需要执行的动作，并执行。

**优先级理由**: 这是指令系统的核心价值 — 教会和自动执行。没有这一步，后续功能无意义。

**独立测试**: 可以通过"教会一条指令 → 触发该指令"的完整流程独立验证。

**验收场景**:

1. **给定** 用户首次教会一条新指令，**当** 用户用不同于触发词的措辞提起（如"推到线上"），**那么** Friday 能通过语义匹配找到"部署"指令并执行
2. **给定** 用户教会了多条指令，**当** 用户说了一段包含关键词的话，**那么** Friday 返回评分最高且超过阈值的指令
3. **给定** 用户输入了不匹配任何指令的内容，**那么** Friday 不触发任何指令，正常处理对话

---

### 用户故事 2 - 查看、管理和删除已学指令 (优先级: P2)

用户可以通过对话（如"你学过哪些指令？"、"把部署那条删了"）查看已学指令列表和删除指定指令。指令以知识条目的形式存储，列表和删除操作走统一的知识库管理接口。

**优先级理由**: 管理能力是必需的，但核心价值在于教和执行（P1）。

**独立测试**: 可以通过"教会指令 → 查看列表 → 删除指令 → 确认列表更新"的流程独立验证。

**验收场景**:

1. **给定** 用户已教会多条指令，**当** 用户问"你学过哪些指令"，**那么** Friday 列出所有已学指令的名称和触发词
2. **给定** 用户要删除某条指令，**当** 用户说"把 xxx 删了"，**那么** Friday 删除该指令并确认删除成功

---

### 边界情况

- 两条指令触发词相似（如"部署"和"部署测试"）时，匹配结果如何排序？
- 指令的动作中包含危险命令（如 `rm -rf`）时，是否仍遵循安全确认策略？
- 知识库中普通笔记和指令条目共存时，检索如何区分？

## 需求

### 核心设计原则

**知识是知识，指令是指令。** 统一存储不等于混淆概念。合并的是底层存储和检索引擎，不是语义边界。无论存储层如何变化，用户感知中"知识"和"指令"始终是两种不同的东西：
- **知识** — 被动信息，用于回答问题和提供上下文（"项目A的截止日期是下周五"）
- **指令** — 主动规则，用于触发执行（"每次我说部署就执行 git push"）

系统必须在存储、检索、展示的各环节保持这一区分，不能因为底层统一就让用户看到指令和知识混在一起。

### 功能需求

- **FR-001**: 指令条目必须作为特殊类型的知识条目存储在知识库中，与普通笔记共存但通过类型标记明确区分
- **FR-002**: 每条指令条目必须包含：名称、触发词、动作列表（命令 + 描述 + 是否需确认）、类型（单步/工作流/条件分支）、关键词。同名或同触发词的指令自动覆盖旧版本（保留创建时间，更新修改时间）
- **FR-003**: 指令匹配必须支持语义检索，用户说"推到线上"能匹配到触发词为"部署"的指令
- **FR-004**: LLM 必须能通过工具调用创建指令条目，且创建指令的工具与创建知识的工具分开（或通过参数明确区分），不能混淆两者
- **FR-005**: LLM 必须能通过工具调用查询已有指令列表（仅指令，不含普通知识）。指令匹配采用被动模式：LLM 通过 `instruction_search` 工具主动检索，由 LLM 自行判断是否需要查找指令及是否执行，不自动触发
- **FR-006**: 指令执行时，动作中的命令必须通过现有执行器的安全策略（安全/首次确认/每次确认）
- **FR-006a**: 普通知识检索不应返回指令条目（除非用户明确问"你学过哪些指令"），指令检索也不应返回普通知识

### 关键实体

- **指令条目 (Instruction Note)**: 知识库中的特殊条目，包含结构化的触发词和动作定义。通过标签（如 `type: instruction`）与普通笔记区分
- **动作 (Action)**: 指令中的操作步骤，包含要执行的命令、描述和是否需要用户确认
- **匹配结果 (Match Result)**: 检索返回的指令条目及匹配评分，用于 LLM 决策是否执行

## 成功标准

### 可衡量结果

- **SC-001**: 用户用不同于触发词的语义表达时，90% 的情况下能正确匹配到对应指令（对比旧系统纯字面匹配的约 40% 覆盖率）
- **SC-002**: 教会一条新指令到可触发的全流程在 2 秒内完成
- **SC-003**: 知识检索和指令检索互不干扰 — 搜知识时不返回指令，查指令时不返回知识笔记

## Clarifications

### Session 2026-06-08

- Q: 指令匹配是自动的（每条消息都检索）还是被动的（LLM 通过工具主动检索）？ → A: 被动匹配 — LLM 通过 `instruction_search` 工具主动检索指令，由 LLM 判断是否需要查指令、是否执行。复用现有工具调用模式，不侵入 Agent 循环。
- Q: 用户重复教会同名/同触发词的指令时如何处理？ → A: 覆盖更新 — 自动覆盖旧版本，保留原创建时间，更新修改时间。
- Q: v1 是否保留全部指令类型（单步/工作流/条件分支）？ → A: 全部保留 — 单步、工作流、条件分支三种类型都迁移到新系统。
- Q: 旧 YAML 指令如何迁移？ → A: 不迁移，直接废弃。旧 `~/.friday/instructions/` 目录下的 YAML 指令不再使用，不提供迁移机制。

## 假设

- 指令条目的结构化数据（触发词、动作列表）存储在知识笔记的 YAML frontmatter 中，内容部分存储人类可读的描述
- 现有知识库的 FTS + ChromaDB 检索能力足以支撑指令匹配，无需额外的匹配引擎
- 旧指令模块的代码（`instruction/`）不再被主流程调用，可以保留用于参考或后续清理
- 指令的执行决策由 LLM 做出（LLM 检索到指令后决定是否执行），而非自动触发
- 旧格式 YAML 指令直接废弃，不提供迁移机制
