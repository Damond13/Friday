## User Input

```text
$ARGUMENTS
```

You **MUST** consider the user input before proceeding (if not empty).

## Outline

1. **定位缺陷目录**：
   - 如果 `$ARGUMENTS` 指定了目录，使用它
   - 否则读取 `.specify/bugfix.json` 的 `bug_directory` 字段
   - 设置 `BUG_DIR` 为解析后的路径

2. **加载上下文**：读取 `BUG_DIR/bug-report.md` 和 `BUG_DIR/diagnosis.md`

3. **评估长期影响**（核心步骤）：
   - **可扩展性评估**：改动是否让该模块更容易扩展？还是会增加未来改动的难度？
   - **未来功能影响**：改动对未来计划中的功能（参考 CLAUDE.md 中的功能规划）是助力还是阻碍？
   - **同类问题预防**：改动是否让同类问题不再可能出现？还是只修了当前这一处？
   - **依赖影响**：改动是否影响其他模块的接口或行为？

4. **设计修复方案**：
   - 基于 diagnosis 的根因，设计最小但面向长期的修复
   - 优先考虑让代码更健康的改法，而非最小补丁
   - 如果诊断结论是方案级问题，建议转入 SDD 流程而非在本流程中强行修复

5. **测试更新评估**：
   - 检查改动涉及的模块是否有对应的自动化测试文件
   - 如果有：在改动清单中列出需要更新的测试文件和新增的测试用例
   - 如果没有：明确标注"该模块暂无自动化测试"，评估是否需要新建

6. **明确边界**：
   - 列出要改的文件和改动内容
   - **同样列出不改的部分**，防止范围蔓延
   - 如果修复需要引入新依赖或重构模块结构，明确说明原因

7. **生成 fixplan.md**：使用 `.specify/templates/fixplan-template.md` 模板

7. **展示草稿**：将修复方案展示给用户，等待确认

8. **确认后写入**：用户确认后写入 `BUG_DIR/fixplan.md`

## Key Rules

- **面向长期**：每个改动都要回答"这对未来是好事还是坏事？"
- **不扩大范围**：修 bug 不是重构的好时机，除非重构本身是根因的一部分
- **不改的部分要明确列出**，防止执行时顺手改了不该改的东西
- 如果修复方案会影响其他模块，必须在改动清单中标注

## Done When

- [ ] 长期影响评估完成（可扩展性、未来功能、同类问题预防）
- [ ] 测试更新评估已完成
- [ ] 修复方案已设计，包含具体文件和改动内容
- [ ] 不改动的部分已明确列出
- [ ] `fixplan.md` 已写入并经用户确认
